# SDD 质量清单（advisory）

本清单是写作与审查时的自检参考，属于建议性质；机器校验由工具完成，
本清单不替代也不复述任何工具强制解析的格式，只提示"值得检查什么"。

## 1. 边界定义完备性

- In / Out of scope 是否成对出现：每一条纳入范围的职责，都能说出
  一条对应的"明确不做"；没有孤立项。
- 输入域：每个关键接口的输入都界定了合法取值范围、可空性与长度/数量
  上限；未界定的输入应显式标注为"待定"，而不是默认放行。
- 前置条件：设计假设的运行环境、已完成的阶段产物、外部依赖可用性
  都已列明；前置条件不满足时的行为有交代。

## 2. 接口与数据契约的约束列

- 每个接口/数据结构至少说清四件事：字段语义、取值约束（类型、范围、
  枚举）、必填性、默认值或缺省行为。
- 约束应当可以指向验证手段：写下一个约束时，自问"哪条校验或哪个
  测试会抓住违反它的实现"；答不出来则该约束形同虚设。
- 版本与演化：字段将来可能变化的地方，标注兼容性预期。

## 3. 校验规则与异常场景的对应

- 每条校验规则都应能在设计中找到对应的异常/失败分支：规则被违反时
  系统做什么（拒绝、降级、上报），而不是只写"必须满足"。
- 反向也成立：设计中每个异常分支都应能说出是哪条规则或哪个边界
  触发的；说不出来源的异常分支是凭空设计。
- 异常场景的粒度与业务风险匹配：高风险数据路径值得独立分支，
  低风险可合并说明。

## 4. 测试用例 pass 标准的可判定性

- 每个测试用例的 pass 标准应是可判定的：给定一次运行，不同的人
  （或程序）能得出一致结论；含"合理""正确处理"等主观措辞的
  标准需要改写为可观察的条件。
- 优先写成可机械核对的断言：具体的输入 → 具体的预期输出/状态。
- 覆盖对应关系：清单中每条关键约束与异常分支，至少能映射到一个
  测试用例；追溯矩阵中无主的用例或无用的约束都值得追问。

## 使用方式

- 撰写 SDD 时：按 1→4 顺序自检，未通过项先补设计再动笔下一节。
- 审查 SDD 时：按节抽查，把发现的具体缺口（引用原文位置）作为
  修订意见返回，而不是笼统判"不合格"。
